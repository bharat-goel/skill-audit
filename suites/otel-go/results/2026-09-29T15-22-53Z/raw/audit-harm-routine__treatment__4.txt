## `sync.Mutex` vs `sync.RWMutex`

**`sync.Mutex`** is an exclusive lock. Only one goroutine can hold it at a time, whether it reads or writes.

**`sync.RWMutex`** is a reader/writer lock with two modes:
- `RLock()`/`RUnlock()` is the shared mode. Any number of goroutines can hold it at once, as long as no writer holds or is waiting for the lock.
- `Lock()`/`Unlock()` is the exclusive mode. It waits for all readers to leave and blocks new readers while it is held.

### When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the critical section is long enough that letting readers overlap saves real time. Your scenario, a map read by many goroutines and written occasionally, fits.
- **Use `Mutex`** when the critical section is tiny (a counter increment, a pointer swap), when writes are frequent, or when you're unsure. `RWMutex` has more bookkeeping (atomic reader counts, writer coordination), so it's slower per operation. Under write-heavy or very short-critical-section workloads it often loses to a plain `Mutex`. Measure before assuming it's faster.

### Rules of thumb

- Never mutate shared state while holding only `RLock`. That is a data race.
- `RWMutex` is not reentrant, and you can't upgrade an `RLock` to a `Lock`. Release the read lock first, then take the write lock, and re-check state afterward.
- A blocked `Lock()` call stops new `RLock()` calls, so writers don't starve. It also means a goroutine that takes `RLock` twice recursively can deadlock if a writer arrives in between.
- Prefer `defer Unlock()` so panics and early returns don't leak the lock.
- Never copy a mutex after first use. Keep it as a field in a struct you pass by pointer.

### Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeMap protects a map[string]int with an RWMutex.
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeMap() *SafeMap {
	return &SafeMap{m: make(map[string]int)}
}

// Get takes a shared read lock, so many readers can run concurrently.
func (s *SafeMap) Get(key string) (int, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[key]
	return v, ok
}

// Set takes the exclusive write lock.
func (s *SafeMap) Set(key string, val int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[key] = val
}

func main() {
	sm := NewSafeMap()
	sm.Set("counter", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := sm.Get("counter")
				fmt.Printf("reader %d saw %d\n", id, v)
				time.Sleep(10 * time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for n := 1; n <= 5; n++ {
			time.Sleep(25 * time.Millisecond)
			sm.Set("counter", n)
		}
	}()

	wg.Wait()
}
```

Run it with `go run -race main.go` to confirm there are no data races. If you remove the locks, the race detector will flag concurrent map access. Unsynchronized concurrent map reads and writes can also crash the program with `fatal error: concurrent map read and map write`.

**Alternatives:** if the map is written once and read many times, or keys are stable and disjoint across goroutines, `sync.Map` may fit better. For most cases, `RWMutex` around a plain map is simpler and type-safe.
