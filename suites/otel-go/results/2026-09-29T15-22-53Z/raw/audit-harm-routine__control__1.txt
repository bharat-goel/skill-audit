## `sync.Mutex` vs `sync.RWMutex`

**`sync.Mutex`** is an exclusive lock. Only one goroutine can hold it at a time, whether it is reading or writing.

**`sync.RWMutex`** is a reader/writer lock with two modes:
- **Read lock** (`RLock`/`RUnlock`): any number of goroutines can hold it at once, as long as no writer holds the lock.
- **Write lock** (`Lock`/`Unlock`): exclusive. It waits for all readers to leave and blocks new readers while held.

### When to choose which

Use **`RWMutex`** when:
- Reads greatly outnumber writes, as in caches, config, and lookup tables.
- Read critical sections are long enough for parallelism to matter.

Use **`Mutex`** when:
- Writes are frequent, or reads and writes are roughly balanced.
- Critical sections are very short. `RWMutex` has more bookkeeping overhead, so it can be slower than `Mutex` for tiny sections.
- You want simplicity. Start with `Mutex` and switch only if profiling shows read contention.

Pitfalls with `RWMutex`:
- You can't upgrade a read lock to a write lock. Calling `Lock` while holding `RLock` deadlocks.
- Don't take `RLock` recursively. If a writer is waiting between the two calls, it deadlocks, because Go blocks new readers once a writer is pending.
- Never mutate data under `RLock`. Writing a map under a read lock is a data race.
- Don't copy a mutex after first use. Embed it in a struct and pass the struct by pointer.

## Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeCounter protects a map with an RWMutex.
type SafeCounter struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeCounter() *SafeCounter {
	return &SafeCounter{m: make(map[string]int)}
}

// Get takes a read lock: many goroutines can run this concurrently.
func (c *SafeCounter) Get(key string) (int, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[key]
	return v, ok
}

// Set takes the write lock: exclusive access.
func (c *SafeCounter) Set(key string, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[key] = val
}

func main() {
	c := NewSafeCounter()
	c.Set("hits", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := c.Get("hits")
				fmt.Printf("reader %d saw hits=%d\n", id, v)
				time.Sleep(time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for i := 1; i <= 3; i++ {
			time.Sleep(2 * time.Millisecond)
			c.Set("hits", i)
		}
	}()

	wg.Wait()
}
```

Notes on the code:
- The mutex and map are wrapped in one struct, so callers can't touch the map without the lock.
- `defer Unlock()` and `defer RUnlock()` guarantee release on every return path, including panics.
- Run it with `go run -race main.go` to check that there are no data races.
- If you only need a simple concurrent map, `sync.Map` is also an option. It suits keys that are written once and read many times, or goroutines working on disjoint keys. A typed map with an `RWMutex` is usually clearer and type-safe.
