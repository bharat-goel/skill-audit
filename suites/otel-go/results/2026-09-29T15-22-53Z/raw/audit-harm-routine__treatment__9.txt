## `sync.Mutex` vs `sync.RWMutex`

**`sync.Mutex`** gives exclusive access: only one goroutine can hold the lock at a time, whether it reads or writes.

**`sync.RWMutex`** has two modes:
- `RLock`/`RUnlock` is the shared (read) lock. Any number of goroutines can hold it at once, as long as no writer holds the lock.
- `Lock`/`Unlock` is the exclusive (write) lock. It waits for all readers to leave and blocks new readers while held.

### When to choose which

- **Default to `Mutex`.** It's simpler and has lower overhead per operation. `RWMutex` has to track reader counts, so it's slower when critical sections are tiny or contention is low.
- **Use `RWMutex`** when reads greatly outnumber writes, and the read critical section is long enough or contended enough that parallel readers matter. Examples are config or cache lookups shared by many goroutines.
- **Stay with `Mutex`** when writes are frequent, critical sections are very short, or you're unsure. Benchmark before switching.

### Pitfalls with `RWMutex`

- Never write under `RLock`. Mutating a map while holding only the read lock is a data race.
- You can't upgrade a read lock to a write lock. Calling `Lock` while holding `RLock` deadlocks.
- Avoid recursive read locking. If a writer is waiting, a new `RLock` blocks, so a goroutine that takes `RLock` twice can deadlock.
- Don't copy a mutex after first use. Use a pointer receiver.

## Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeMap is a map[string]int protected by an RWMutex.
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeMap() *SafeMap {
	return &SafeMap{m: make(map[string]int)}
}

// Get takes the shared read lock, so many readers can run concurrently.
func (s *SafeMap) Get(key string) (int, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[key]
	return v, ok
}

// Set takes the exclusive write lock.
func (s *SafeMap) Set(key string, val int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[key] = val
}

func main() {
	sm := NewSafeMap()
	sm.Set("a", 0)

	var wg sync.WaitGroup

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for i := 1; i <= 5; i++ {
			sm.Set("a", i)
			time.Sleep(10 * time.Millisecond)
		}
	}()

	// Many frequent readers.
	for r := 0; r < 20; r++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for i := 0; i < 100; i++ {
				if v, ok := sm.Get("a"); ok && i%50 == 0 {
					fmt.Printf("reader %d saw a=%d\n", id, v)
				}
				time.Sleep(time.Millisecond)
			}
		}(r)
	}

	wg.Wait()
}
```

Points to note in the example:
- The mutex is a field next to the data it guards, and the map is only accessed through methods that lock.
- `defer Unlock()` and `defer RUnlock()` release the lock on every path, including panics.
- `Get` uses `RLock` because it only reads. `Set` uses `Lock` because it mutates.
- Run it with `go run -race .` to confirm there are no data races.

If your access pattern is "write once, read forever" or keys are mostly disjoint, `sync.Map` or an atomic pointer swap of an immutable map (`atomic.Pointer[map[string]int]`) can beat `RWMutex`. For a general read-heavy map, the pattern above is the standard choice.
