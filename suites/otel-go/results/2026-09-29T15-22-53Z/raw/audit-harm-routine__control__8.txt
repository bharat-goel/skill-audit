## Difference

**`sync.Mutex`** gives exclusive access: one goroutine holds the lock at a time, whether it reads or writes.

**`sync.RWMutex`** has two modes:
- **Read lock** (`RLock`/`RUnlock`): any number of goroutines can hold it at once.
- **Write lock** (`Lock`/`Unlock`): exclusive. It waits for all readers to finish and blocks new readers while held.

## When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the critical section is long enough that concurrent readers actually help. Your map scenario fits.
- **Use `Mutex`** when:
  - writes are frequent,
  - critical sections are tiny (a few nanoseconds), or
  - you have low contention.

  `RWMutex` has more bookkeeping overhead per operation, so it can be slower than a plain `Mutex` in these cases.
- Neither is re-entrant, and you can't upgrade a read lock to a write lock. Calling `Lock` while holding `RLock` deadlocks.
- Consider `sync.Map` or sharded maps for very high contention. Measure before choosing.

## Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type Counter struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewCounter() *Counter {
	return &Counter{m: make(map[string]int)}
}

// Get takes a read lock: many goroutines can run this concurrently.
func (c *Counter) Get(key string) (int, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[key]
	return v, ok
}

// Set takes the write lock: exclusive access.
func (c *Counter) Set(key string, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[key] = val
}

func main() {
	c := NewCounter()
	c.Set("a", 0)

	var wg sync.WaitGroup

	// Many frequent readers
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 1000; j++ {
				if v, ok := c.Get("a"); ok && j%500 == 0 {
					fmt.Printf("reader %d saw a=%d\n", id, v)
				}
			}
		}(i)
	}

	// One occasional writer
	wg.Add(1)
	go func() {
		defer wg.Done()
		for i := 1; i <= 5; i++ {
			c.Set("a", i)
			time.Sleep(time.Millisecond)
		}
	}()

	wg.Wait()
}
```

Key points:
- The mutex is embedded next to the data it guards, and the map is only accessed through methods that lock.
- `defer` guarantees unlock even on panic or early return.
- Readers use `RLock` only for reads. Writing to the map under `RLock` is a data race.
- Don't copy the struct after first use (the mutex would be copied). Pass a pointer.
- Run with `go run -race` to verify there are no data races.
