## Mutex vs RWMutex

**`sync.Mutex`** allows exactly one goroutine at a time into the critical section, whether it's reading or writing. Methods: `Lock`, `Unlock`, `TryLock`.

**`sync.RWMutex`** distinguishes two modes:
- **Read lock** (`RLock`/`RUnlock`): any number of goroutines can hold it at once, as long as no writer holds or is waiting for the lock.
- **Write lock** (`Lock`/`Unlock`): exclusive. It waits for all current readers to finish and blocks new readers while it waits or holds the lock, which prevents writer starvation.

### When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the critical section does enough work that parallel readers help (for example, a config or cache map read by many goroutines and updated rarely).
- **Use `Mutex`** when the critical section is tiny, when writes are frequent, or when you're unsure. `RWMutex` has more bookkeeping overhead, so with short sections or a mixed workload it can be slower than a plain `Mutex`. Measure before switching.

Pitfalls with `RWMutex`:
- Don't mutate data while holding only `RLock`. That is a data race.
- You can't upgrade a read lock to a write lock. Release `RLock` first, then take `Lock`. Calling `Lock` while holding `RLock` deadlocks.
- Avoid recursive read locking. If a writer is waiting between the two `RLock` calls, the second one blocks and you deadlock.
- Never copy a mutex after first use. Keep it in a struct and use pointer receivers.

## Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeCounter protects a map with an RWMutex.
type SafeCounter struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeCounter() *SafeCounter {
	return &SafeCounter{m: make(map[string]int)}
}

// Get takes a read lock: many goroutines can run this concurrently.
func (c *SafeCounter) Get(key string) (int, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[key]
	return v, ok
}

// Set takes the exclusive write lock.
func (c *SafeCounter) Set(key string, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[key] = val
}

func main() {
	c := NewSafeCounter()
	c.Set("hits", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := c.Get("hits")
				fmt.Printf("reader %d saw hits=%d\n", id, v)
				time.Sleep(time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for n := 1; n <= 3; n++ {
			time.Sleep(2 * time.Millisecond)
			c.Set("hits", n)
		}
	}()

	wg.Wait()
}
```

Key points:
- The mutex lives inside the struct next to the data it guards, and callers only reach the map through methods.
- `defer Unlock`/`RUnlock` releases the lock on every return path, including panics.
- Run it with `go run -race .` to confirm there are no data races.

If you only need a read-mostly map and no invariants across keys, `sync.Map` is another option. For most cases, the typed `RWMutex` + `map` above is clearer and type-safe.
