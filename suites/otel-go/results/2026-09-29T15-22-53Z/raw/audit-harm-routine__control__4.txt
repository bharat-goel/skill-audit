## Mutex vs RWMutex

**`sync.Mutex`** allows exactly one goroutine in the critical section at a time, whether it's reading or writing.

**`sync.RWMutex`** has two modes:
- **Read lock (`RLock`/`RUnlock`)**: any number of goroutines can hold it at once, provided no writer holds or is waiting for the lock.
- **Write lock (`Lock`/`Unlock`)**: exclusive. It waits for current readers to finish and blocks new readers while it waits or holds the lock.

### When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the read-side critical section does real work (a map lookup with contention from many cores, for example). Concurrent readers then don't serialize.
- **Use `Mutex`** when the critical section is tiny, writes are frequent, or the read/write ratio is close to even. `RWMutex` has more bookkeeping (atomic counters, reader-count coordination), so it's slower per operation than `Mutex`. With little contention or a mixed workload it can lose.
- Other things to know:
  - You can't upgrade an `RLock` to a `Lock`. Releasing and re-acquiring is required, and the state may change in between.
  - Don't take `RLock` recursively. If a writer is waiting between the two calls, you deadlock.
  - Neither type may be copied after first use. Embed it in a struct and pass the struct by pointer.
  - Measure before assuming `RWMutex` is faster. For simple counters, `sync/atomic` may be better still. For write-once, read-many caches, `sync.Map` may fit.

## Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeCounter guards a map with an RWMutex.
type SafeCounter struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeCounter() *SafeCounter {
	return &SafeCounter{m: make(map[string]int)}
}

// Get takes a shared read lock, so many readers can run concurrently.
func (c *SafeCounter) Get(key string) (int, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[key]
	return v, ok
}

// Set takes the exclusive write lock.
func (c *SafeCounter) Set(key string, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[key] = val
}

func main() {
	c := NewSafeCounter()
	c.Set("hits", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := c.Get("hits")
				fmt.Printf("reader %d saw hits=%d\n", id, v)
				time.Sleep(time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for n := 1; n <= 3; n++ {
			time.Sleep(2 * time.Millisecond)
			c.Set("hits", n)
		}
	}()

	wg.Wait()
}
```

### Key points in the snippet

- The mutex and map live together in one struct, and all access goes through methods. No code touches `m` without holding the lock.
- `defer` guarantees the unlock even if the code panics or returns early.
- Readers use `RLock`, and the writer uses `Lock`. Using `RLock` around a write is a data race, and the race detector (`go run -race`) will catch it.
- The struct is used via pointer, so the mutex is never copied.
