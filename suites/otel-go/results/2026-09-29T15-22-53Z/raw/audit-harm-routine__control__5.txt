## Mutex vs RWMutex

**`sync.Mutex`** gives exclusive access: one goroutine holds the lock at a time, whether it's reading or writing.

**`sync.RWMutex`** distinguishes two modes:
- `RLock()`/`RUnlock()`: a *shared* read lock. Any number of goroutines can hold it at once.
- `Lock()`/`Unlock()`: an *exclusive* write lock. It waits for all readers to leave and blocks new readers and writers while held.

### When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the critical section does real work, so parallel readers actually pay off. A read-mostly cache or config map is the classic case.
- **Use `Mutex`** when:
  - writes are frequent, or the read/write ratio is close to even;
  - critical sections are tiny (a counter increment). `RWMutex` has more bookkeeping overhead, so it can be *slower* than `Mutex` here;
  - you want simplicity. `RWMutex` is easy to misuse.

Pitfalls with `RWMutex`:
- Don't upgrade a read lock to a write lock (`RLock` then `Lock`) in the same goroutine. It deadlocks.
- Don't take `RLock` recursively. If a writer is waiting between the two calls, it deadlocks, because Go blocks new readers once a writer is pending.
- Never write to the protected data while holding only `RLock`.
- Don't copy a mutex after first use. Embed it in a struct and use pointer receivers.

## Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeMap protects a map with an RWMutex.
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeMap() *SafeMap {
	return &SafeMap{m: make(map[string]int)}
}

// Get takes a shared lock, so many readers run concurrently.
func (s *SafeMap) Get(key string) (int, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[key]
	return v, ok
}

// Set takes the exclusive lock, so it blocks readers and other writers.
func (s *SafeMap) Set(key string, val int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[key] = val
}

func main() {
	sm := NewSafeMap()
	sm.Set("hits", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := sm.Get("hits")
				fmt.Printf("reader %d saw %d\n", id, v)
				time.Sleep(10 * time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for n := 1; n <= 3; n++ {
			time.Sleep(20 * time.Millisecond)
			sm.Set("hits", n)
		}
	}()

	wg.Wait()
}
```

Key points:
- The mutex and map sit together in one struct, and callers never touch the map directly.
- `defer` guarantees the unlock even if the code panics or returns early.
- Run it with `go run -race main.go` to confirm there are no data races. Removing the locks would make the race detector flag the code.

If you also need read-modify-write operations (such as increment), put them inside a single `Lock()` section. Doing `Get` then `Set` separately isn't atomic.
