## `sync.Mutex` vs `sync.RWMutex`

**`sync.Mutex`** is a plain mutual-exclusion lock. Only one goroutine can hold it at a time, whether it's reading or writing.

**`sync.RWMutex`** is a reader/writer lock with two modes:
- **Read lock** (`RLock`/`RUnlock`): any number of goroutines can hold it at once, as long as no writer holds it.
- **Write lock** (`Lock`/`Unlock`): exclusive. It waits for all readers to leave and blocks new readers while it's held.

### When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the read critical section does real work. Readers run in parallel, which improves throughput.
- **Use `Mutex`** when:
  - the critical section is tiny, such as incrementing a counter or reading one field. `RWMutex` has more bookkeeping overhead, so it's often slower than `Mutex` here;
  - writes are frequent, or reads and writes are roughly balanced;
  - you want the simplest option. Start with `Mutex` and switch only if profiling shows read contention.

### Gotchas with `RWMutex`

- **Don't mutate under `RLock`.** Writing to the map while holding only a read lock is a data race.
- **No upgrading.** You can't go from `RLock` to `Lock` while holding it, because that deadlocks. Release the read lock first, then take the write lock, and re-check state after you get it.
- **No recursive read locking.** If a writer is waiting, a second `RLock` in the same goroutine blocks, because new readers queue behind a pending writer. That can deadlock.
- **Don't copy a mutex.** Embed it in a struct and pass the struct by pointer.

### Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeCounter is a map[string]int guarded by an RWMutex.
type SafeCounter struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeCounter() *SafeCounter {
	return &SafeCounter{m: make(map[string]int)}
}

// Get takes a read lock, so many goroutines can call it concurrently.
func (c *SafeCounter) Get(key string) (int, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[key]
	return v, ok
}

// Set takes the exclusive write lock.
func (c *SafeCounter) Set(key string, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[key] = val
}

func main() {
	c := NewSafeCounter()
	c.Set("hits", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := c.Get("hits")
				fmt.Printf("reader %d saw hits=%d\n", id, v)
				time.Sleep(10 * time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for n := 1; n <= 3; n++ {
			time.Sleep(20 * time.Millisecond)
			c.Set("hits", n)
		}
	}()

	wg.Wait()
}
```

Key points in the code:
- The map is only touched inside methods that hold the lock, and callers never see the raw map.
- `defer` guarantees the unlock even if the code panics or returns early.
- Run it with `go run -race .` to confirm there are no data races.

If you also need read-modify-write, such as incrementing a value, do it under a single `Lock` in one method. Doing `Get` and then `Set` separately leaves a race window between the two calls.
