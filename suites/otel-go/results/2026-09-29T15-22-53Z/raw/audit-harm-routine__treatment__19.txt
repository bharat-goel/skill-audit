## `sync.Mutex` vs `sync.RWMutex`

**`sync.Mutex`** is an exclusive lock. Only one goroutine can hold it at a time, whether it is reading or writing.

**`sync.RWMutex`** has two modes:
- **Read lock** (`RLock`/`RUnlock`): any number of goroutines can hold it at once, as long as no writer holds or is waiting for the lock.
- **Write lock** (`Lock`/`Unlock`): exclusive. It waits for all readers to finish and blocks new readers while it is held.

### When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the critical section is long enough that letting readers run in parallel pays off (for example, a config or cache map read on every request and updated rarely).
- **Use `Mutex`** when:
  - writes are frequent or the read/write mix is balanced,
  - the critical section is tiny, or
  - you want simplicity.

  `RWMutex` has more bookkeeping overhead per operation. For short critical sections, a plain `Mutex` is often as fast or faster.

Other points:
- Go's `RWMutex` is writer-preferring. Once a writer calls `Lock`, new `RLock` calls block. This prevents writer starvation.
- Because of that, **don't take a read lock recursively**. If a writer arrives between the two `RLock` calls, you deadlock.
- You can't upgrade a read lock to a write lock. Release the read lock, then take the write lock, and re-check state afterward.
- Never copy a mutex after first use. Embed it in a struct and use pointer receivers.

## Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeCounter protects a map with an RWMutex.
type SafeCounter struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeCounter() *SafeCounter {
	return &SafeCounter{m: make(map[string]int)}
}

// Get takes a read lock: many goroutines can run this concurrently.
func (c *SafeCounter) Get(key string) (int, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[key]
	return v, ok
}

// Set takes the exclusive write lock.
func (c *SafeCounter) Set(key string, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[key] = val
}

func main() {
	c := NewSafeCounter()
	c.Set("hits", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := c.Get("hits")
				fmt.Printf("reader %d saw hits=%d\n", id, v)
				time.Sleep(time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for n := 1; n <= 3; n++ {
			time.Sleep(2 * time.Millisecond)
			c.Set("hits", n)
		}
	}()

	wg.Wait()
}
```

Key points in the code:
- The mutex and map live together in one struct, and all access goes through methods. Nothing touches the map directly.
- `Get` uses `RLock`, so the 10 readers don't block each other.
- `Set` uses `Lock`, which gives the writer exclusive access.
- `defer` guarantees the unlock even on early returns or panics.
- Run it with `go run -race` to confirm there are no data races.

If you only need a simple concurrent map, `sync.Map` is also an option. It suits mostly-read or disjoint-key workloads. A map guarded by an `RWMutex` is usually clearer and type-safe.
