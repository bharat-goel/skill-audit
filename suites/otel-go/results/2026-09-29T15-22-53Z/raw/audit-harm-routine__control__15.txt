## Mutex vs RWMutex

**`sync.Mutex`** gives exclusive access: only one goroutine can hold the lock at a time, whether it's reading or writing.

**`sync.RWMutex`** distinguishes two modes:
- `RLock()`/`RUnlock()`: shared read lock. Any number of goroutines can hold it simultaneously.
- `Lock()`/`Unlock()`: exclusive write lock. It waits for all readers to finish and blocks new readers while held.

### When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the critical section is non-trivial, so concurrent readers actually gain throughput.
- **Use `Mutex`** when the critical section is tiny, when writes are frequent, or when you're unsure. `RWMutex` has more bookkeeping overhead, so with short critical sections or write-heavy workloads it can be *slower* than a plain `Mutex`. Default to `Mutex` and switch only if profiling shows read contention.

Pitfalls with `RWMutex`:
- You can't upgrade a read lock to a write lock. Calling `Lock()` while holding `RLock()` deadlocks. Release the read lock first, then acquire the write lock, and re-check state.
- Don't take `RLock` recursively. If a writer is waiting between the two calls, the second `RLock` blocks and you deadlock.
- Never mutate shared data under `RLock`.
- Don't copy a mutex after first use. Embed it in a struct and pass the struct by pointer.

## Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// Cache is a map guarded by an RWMutex.
type Cache struct {
	mu   sync.RWMutex
	data map[string]int
}

func NewCache() *Cache {
	return &Cache{data: make(map[string]int)}
}

// Get takes a shared lock, so many readers can run concurrently.
func (c *Cache) Get(key string) (int, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.data[key]
	return v, ok
}

// Set takes the exclusive lock, blocking all readers and writers.
func (c *Cache) Set(key string, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[key] = val
}

func main() {
	c := NewCache()
	c.Set("hits", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := c.Get("hits")
				fmt.Printf("reader %d saw hits=%d\n", id, v)
				time.Sleep(time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for n := 1; n <= 3; n++ {
			time.Sleep(2 * time.Millisecond)
			c.Set("hits", n)
		}
	}()

	wg.Wait()
}
```

Key points in the snippet:
- The mutex and map live together in one struct, and all access goes through methods, so no code can touch the map without the lock.
- `defer` guarantees the unlock even if the code panics or returns early.
- Run it with `go run -race .` to confirm there are no data races. Removing the locks will make the race detector flag the concurrent map access (and Go may also crash with `fatal error: concurrent map read and map write`).
