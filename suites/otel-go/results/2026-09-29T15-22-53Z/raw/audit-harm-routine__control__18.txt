## Mutex vs RWMutex

**`sync.Mutex`** allows exactly one goroutine at a time into the critical section, whether it is reading or writing. It has `Lock()` and `Unlock()`.

**`sync.RWMutex`** distinguishes two kinds of access:
- **Write lock** (`Lock`/`Unlock`): exclusive. It blocks all other readers and writers.
- **Read lock** (`RLock`/`RUnlock`): shared. Any number of readers can hold it at once, but no writer can.

### When to choose which

- **Use `RWMutex`** when reads greatly outnumber writes and the critical section is long enough that parallel readers actually help. Examples are caches, config or lookup tables, and registries.
- **Use `Mutex`** when:
  - writes are frequent, or reads and writes are roughly balanced;
  - the critical section is tiny, such as incrementing a counter. `RWMutex` bookkeeping is more expensive, so it can be slower than a plain `Mutex` here.
  - you want simplicity. `Mutex` has fewer ways to go wrong.

Caveats with `RWMutex`:
- You can't upgrade a read lock to a write lock. Calling `Lock()` while holding `RLock()` deadlocks.
- Don't take `RLock` recursively. If a writer is waiting between the two calls, it deadlocks, because Go blocks new readers once a writer is pending.
- Never write while holding only `RLock`. That is a data race.
- For a map with a read-mostly workload, `sync.Map` is another option, but a map guarded by `RWMutex` is typed and easier to reason about.

### Example

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SafeMap is a map[string]int guarded by an RWMutex.
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewSafeMap() *SafeMap {
	return &SafeMap{m: make(map[string]int)}
}

// Get takes a shared read lock; many goroutines can run this concurrently.
func (s *SafeMap) Get(key string) (int, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[key]
	return v, ok
}

// Set takes the exclusive write lock.
func (s *SafeMap) Set(key string, val int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[key] = val
}

func main() {
	sm := NewSafeMap()
	sm.Set("hits", 0)

	var wg sync.WaitGroup

	// Many frequent readers.
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 5; j++ {
				v, _ := sm.Get("hits")
				fmt.Printf("reader %d saw hits=%d\n", id, v)
				time.Sleep(5 * time.Millisecond)
			}
		}(i)
	}

	// One occasional writer.
	wg.Add(1)
	go func() {
		defer wg.Done()
		for n := 1; n <= 3; n++ {
			time.Sleep(15 * time.Millisecond)
			sm.Set("hits", n)
			fmt.Printf("writer set hits=%d\n", n)
		}
	}()

	wg.Wait()
}
```

Points to note:
- Every access to the map goes through methods that take the lock, so callers never touch `m` directly.
- `defer` guarantees the unlock even if the code panics.
- The mutex is a field, not copied. Pass `*SafeMap` and never copy a struct that contains a mutex.
- Run it with `go run -race main.go` to confirm there are no data races.
