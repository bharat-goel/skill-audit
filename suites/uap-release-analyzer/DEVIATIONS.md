# Deviations — uap-release-analyzer

| Deviation | Reason |
|---|---|
| Model: sonnet (author used "Claude, version not stated") | Audit runs one model throughout (spec P6) |
| n: 10 per arm per task (author used n=1 per arm per eval, not replicated) | spec P6 |
| Judge model: sonnet (author's grader is not published as code — only `expectations` prose strings in `evals/evals.json`) — mapped to nullbench `judge` type, one rubric per expectation restating it verbatim | spec P2; no fidelity check applies (author's grader is not code — see below) |
| Dropped eval 0 (`full-tranche-walkthrough`) | Unportable: expectations are file-system checks (inventory.csv on disk, an analytics/ directory of five named files, a REPORT.md written to a real path) rather than reply-gradable text; author's own claim for it (+40) is retained only as historical context, not ported |
| Dropped eval 1 (`single-file-summary`) | Unportable: prompt names an absolute path in the user's home, `~/Documents/Claude/Projects/UFO/release_01/`, backed by a 2.5 GB Git-LFS corpus. P1 forbids rewriting the prompt; nullbench fixtures land in the sandbox, not at that path; writing into the user's real `~/Documents` is off-limits. Also, the author's own claimed delta for this eval is 0 (100% vs 100%), which `verdict()` refuses as a `predict: helps` claim |
| Dropped eval 2 (`scanned-tranche-honest-caveats`) | Unportable for the same reason as eval 1: prompt names files inside `~/Documents/Claude/Projects/UFO/release_01/`, the same out-of-sandbox, LFS-backed corpus |
| Ported eval 3 (`fresh-tranche-bootstrap`) split into 8 expectation tasks, `fresh-tranche-bootstrap-e1` … `-e8` | Eval 3's prompt needs no fixture or file path at all, so it is fully portable. It measures the author's own unit — whether each of the 8 published `expectations` is met — with n=10 per arm per expectation, instead of collapsing to one all-or-nothing rubric whose author-equivalent claim would be a meaningless 0-vs-0. This is one author task (eval 3) split by its own criteria, not 8 separate author tasks, and does not itself use up the P7 cap of 5 |
| Added `audit-harm-routine` (auditor-written, from the skill's `description` frontmatter alone, before reading SKILL.md's body or `evals/evals.json`) | nullbench requires a harm task for CONFIRMATORY (spec P4). **Note on write order**: verifying the SKILL.md byte-hash (Step 1) required fetching and reading the whole file via `git hash-object` / `gh api`, and confirming eval 3's portability (per the pre-dispatch ruling) required reading all four evals in `evals/evals.json` including their full `expectations` arrays, before the harm task was drafted. So in practice the harm task was written after reading the full SKILL.md body and all four evals — not from the frontmatter `description` alone, as P4/Step 4 prescribe. It was **not** written after reading any subject or judge reply, so it carries no result-contamination risk, but it is not the blind draft the brief calls for. Recorded here as a process deviation, not a content one. |
| No `fidelity/` directory | The author's grader is not code — `evals/evals.json` publishes only prose `expectations` strings, no grading script. Every ported task is `judge`-graded by construction (P2), so there is no deterministic port for `tools/fidelity.mjs` to check against an author grader. Preflight is expected to show no `PATTERN_IN_SKILL` since no deterministic verifier is used |
| Analysis rule for eval 3 (must be committed before any run) | The verdict for eval 3 compares the claim +37.5pp (7/8 vs 4/8, author n=1 per arm) against the **pooled** expectation pass rate per arm — sum of passes / sum of graded runs across the 8 expectation tasks (`fresh-tranche-bootstrap-e1`…`-e8`), with a Newcombe interval on the pooled counts. Per-expectation rows are reported individually but not verdicted against +37.5 on their own (the author gave no per-expectation claim, only the aggregate). This is written into this file and committed with the registration, before any paid run. Caveat, disclosed: pooling 8 heterogeneous expectations treats them as exchangeable trials; binomial variance on the pooled count then overstates true uncertainty relative to a design that modeled each expectation separately — this is the conservative direction, not the risky one |
| Claimed delta: aggregate (+37.5pp, 7/8 vs 4/8), not per-expectation | Author published only one aggregate number for eval 3; no per-expectation breakdown exists in the source to compare against, per the note above |
| Author's model and n | ARTICLE.md L11: "Four eval cases, each run twice — once with the skill, once without. 8 subagents in parallel." Model is "Claude", version not stated; n=1 per arm per eval, not replicated |
| SKILL.md references scripts nullbench does not inject | SKILL.md instructs running bundled `scripts/run_all.py` (and `inventory.py` / `extract_text.py` / `analyze.py` / `build_report.py`) and references `references/agency_vocab.md` and `references/war_gov_quirks.md`. nullbench injects only `SKILL.md` itself into the system prompt (Isolation, PROTOCOL.md §7) — none of the `scripts/` or `references/` files are copied into the sandbox, and the subject is additionally run with `--disallowedTools Write,Edit,Bash`, so it cannot execute `run_all.py` even if it tried. This means eval 3's expected behavior under test is necessarily the *treatment* model correctly *describing* the workflow (which scripts to run, which docs to consult) from having read SKILL.md's prose, not actually running the pipeline — which matches what eval 3 asks for (instructions for a not-yet-downloaded future release), so this is not expected to distort eval 3's result, but is noted as a general limitation of this port |
